coff / compiler

the compiler

1self-hosted

coff is written in c0 and compiles its own source. the binary built from c0/coff.c0 is called coff1. it is the compiler everything is built with, moonshot's kernel included. that the compiler compiles itself is not proof that it is correct, since a wrong compiler can reproduce itself just as faithfully as a right one. what keeps it honest is the seed compiler it is compared against. TRUST.md in the repository goes into what the self-compiling does and does not prove.

2coff0, the seed

a compiler written in its own language cannot compile itself the first time. something else has to. that something is coff0, a compiler for the same language written in plain C, about 3,300 lines with no build system and no dependencies past the C library. it builds the first coff1. from then on it is the reference. every program in the test corpus is compiled by both. the two outputs have to match byte for byte, error messages included.

coff0 is kept small on purpose. small means any C compiler can build it, which is what makes it possible to build it with several unrelated ones and compare. small also means one person can read all of it. so it does not get retired even though coff1 has long outgrown the need for it. every language feature is written into it first.

3inside the compiler

coff is a straight pipeline with no stage that loops back.

  1. includeevery included file is pasted in, giving one flat buffer of source
  2. lexerthe buffer becomes tokens
  3. parserthe tokens become the whole program as a tree
  4. resolvenames are matched to variables, functions and layout fields while mistakes are reported
  5. code generationthe tree becomes x86-64 assembly text
  6. smedthe text becomes an executable, see smed

the output is assembly text rather than machine code because text can be diffed. two compilers that agree on every character of their assembly agree on everything that matters. a disagreement points at the line where it starts.

4code generation

the code generator is a stack machine at heart. a value is worked out into rax, the left side of an operator waits on the stack while the right side is worked out. the two meet in a register. that is simple to check and slow, so coff takes a few shortcuts when the shape of the code makes them safe. there is no separate optimizer pass, since a pass that rewrites finished assembly has to guess which registers are still in use. a guess is a place for a bug to live.

  • a number or a variable on the right of an operator goes straight into a register instead of round the stack.
  • a comparison used as a condition jumps on the processor's flags instead of making a 0 or 1 first. && and || do the same.
  • a number that fits in 32 bits is written into the instruction itself.
  • for an operator where order does not matter, the side that is simple to load is loaded last.
  • a call loads simple arguments straight into the registers they travel in.
  • a store of a number or a variable keeps its address in rdi while the value is worked out. every other store goes through the stack. every call does too.

coff0 takes exactly the same shortcuts, so the two still agree byte for byte. moonshot's kernel came out a fifth smaller and a frame of its graphics benchmark takes a third less time. each shortcut has a test written to catch it going wrong. each test was broken on purpose to see that it does. the suite as it stood before missed a wrong <= jump completely, which is why that matters.

the busiest local variables live in registers. coff generates each function twice. the first time only counts and never writes anything. it counts how often each variable is used, a use counting eight times as much for each loop around it. the five heaviest that are used more than a couple of times get rbx and r12 to r15, the registers a function has to hand back the way it found them, so a call in between leaves them alone. the second time is the real one. this is safe because c0 cannot take a variable's address, so nothing can reach a local except by its name. a local in a register is compared, added to and assigned in place, without a trip through rax. the kernel came out about ten percent smaller. a check in the test suite makes sure every function saves and restores each register it keeps a local in.

the assembly leaves the compiler through a buffer of 64 kilobytes instead of one system call per piece of text, which makes coff compile about twice as fast.

5the command line

both compilers refuse an argument that starts with - and is not --elf or -I, before they open anything. a -I with no directory has a message of its own. so do more than eight of them. the refusal exists because a compiler that took -x for the input and the next name for the output once compiled over its own source. coff0 no longer has the -t and -a options that dumped tokens and the tree.

6two targets

by default coff writes assembly for linux, with linux system call numbers. with --elf it writes the same assembly for moonshot's ring 3, where user programs run. three things differ. a program exits through moonshot's own exit call, print goes to the kernel's debug output and alloc asks the kernel for memory from the process's own heap. the file builtins become moonshot's own file calls. port input and output are refused. on top of that come the moonshot builtins listed on the language page.

smed then links it with --base 0x80000000, where moonshot maps user programs. that address is above two gigabytes, which is why smed reaches a global through the instruction pointer instead of through an absolute address. the processor sign-extends an absolute 32-bit address, so it cannot see the second gigabyte at all. the first program built this way died on its first store.

7one backend, on purpose

--elf is a handful of emitted lines that differ in a system call number. coff0 has the same flag. it is diffed like everything else, so a program for moonshot gets exactly the checking a program for linux gets.it was not always so. coff once had a second backend that wrote machine code byte by byte for moonshot, with its own labels, its own call patching and its own ELF writer. coff0 never had one, so no comparison ever looked at it. the whole test suite proved nothing about the path every ring-3 program took. three silent wrong-code bugs were found in it by eye while the suite stayed green. once smed existed the fix was to delete that backend rather than to test it, which took five hundred lines out of the compiler.

8error messages

coff1: hello.c0:3: undeclared variable 'y'

a program with a mistake in it gets the file, the line and a message. coff1 says word for word what coff0 says. that is checked rather than hoped for. every program in the test suite that is meant to fail goes through both compilers. the run fails if the messages differ once each compiler's own name is taken off the front. there are seventy-two of them. two compilers can agree while both point at the wrong line, so twenty-seven of them also have the exact message they must give written down beside them.

the line is the harder part. include pastes every file into one buffer before the lexer starts, so a position in that buffer says nothing about which file it came from. the include step leaves a small table behind with one entry for every place it started copying from a file. the lexer walks it as it reads. a mistake on line 97 of a file the kernel pulls in comes out as that file and line 97, from both compilers.

9how it is tested

run_tests.sh runs over 370 checks. every test program is compiled, assembled, linked and run. its exit code is compared with what the test expects, plus its exact output or exact error where the test says. then coff1 is compared byte for byte with coff0 over every compile in ddc_entries.sh, the one list of what the build compiles. it holds the tests and the sources. when moonshot is checked out next to coff it also holds every program, test and kernel variant its build compiles, with the flags the build gives it. the audit reads the same list and fails when a build script compiles something the list does not name. a program that is meant to fail is compared on its message and its exit code. coff1 has no separate lexer and parser to compare any more, so its front end is checked end to end, by what it does to every file in the list. last comes the fixpoint, the compiler compiling itself three generations deep with every generation identical.

what no comparison can show is that a program behaves right once it runs on moonshot, only that both compilers agree about it. that is covered in moonshot's own tree, by small programs whose exit code only comes out right if the code generator is right. they cover chained control flow, short-circuit operators with a side effect that proves the right side was skipped, all six argument registers, recursion, layouts, reading files, the kernel's font and globals holding a function to call through.
